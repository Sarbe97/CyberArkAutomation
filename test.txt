# Technical White Paper: CyberArk Mainframe (IBM z/OS) Credential Management Integration

**Document Version:** 1.0  
**Target Platform:** IBM z/OS (Communications Server / Enterprise LPAR)  
**Security Subsystems:** CA Top Secret (TSS) / IBM RACF / ACF2  
**Source Infrastructure:** CyberArk Central Policy Manager (CPM)  
**Target Infrastructure:** Enterprise Mainframe LPAR (`<lpar-hostname>`)  

---

## 1. Executive Summary & Objective

The objective of this initiative is to automate the credential lifecycle (Verification, Change, and Reconciliation) of privileged IBM z/OS mainframe accounts using the CyberArk Central Policy Manager (CPM). 

Enterprise security policies mandate that all credential management activities must use **end-to-end encrypted transport (TLS/SSH)** to prevent cleartext password transmission across the corporate network. 

During initial connectivity and protocol negotiation testing from the CPM to the target LPAR, network routing was verified on TCP Port 21 (FTP), but in-line TLS encryption (`AUTH TLS`) and standard SSH (TCP Port 22) were unavailable. This paper documents the architecture, login mechanisms, empirical test findings, root-cause analysis of the `534` rejection, and formal technical questions submitted to the Mainframe Systems Programming team.

---

## 2. Mainframe Account Integration Architectures & Login Types

CyberArk supports two core architectures to manage IBM z/OS credentials:

```

┌────────────────────────┐     │  ┌───────────────────────┐   ┌──────────────────────┐  │

│    (<cpm-ip>)          ├─────┼─>│ Services (OpenSSH)    ├──>│ CA Top Secret / RACF │  │

│  • TPC (plink.exe)     │     │  └───────────────────────┘   └──────────────────────┘  │
```

---

### Architecture Option 1: Interactive SSH via z/OS UNIX System Services (`Policy-OS390SSH`)
* **Execution Engine**: `CyberArk.TPC.exe` (Terminal Plugin Controller) using `plink.exe`.
* **Transport**: TCP Port 22 (SSH-2) or a dedicated custom SSH port.
* **Target Shell**: z/OS UNIX System Services (USS) shell (`/bin/sh` or `/bin/tsosh`).
* **Supported Login Types**:
  1. **Direct Login**: CPM logs in directly with the target account and executes the USS `passwd <username>` command.
  2. **Logon Account (Dual-Account)**: For target accounts restricted from direct interactive login, CPM logs in using an unprivileged Logon account (`extrapass1`) and elevates/switches user:
     ```bash
     su - <username>
     passwd <username>
     ```
  3. **Reconcile Account**: A security administrator account invokes TSO commands to reset credentials without requiring the existing password:
     ```bash
     tsocmd "TSS REPLACE(<username>) PASSWORD(<newpassword>)"
     ```

---

### Architecture Option 2: JES Batch Job Submission via Encrypted FTP (`Policy-OS390FTP`)
* **Execution Engine**: `pmOS390FTP.exe`.
* **Transport**: TCP Port 21 (with Explicit TLS `AUTH TLS`) or a dedicated EFTP/FTPS port.
* **Mechanism**: Rather than interactive terminal screen scraping, CyberArk uses **JES (Job Entry Subsystem) batch job injection** through the IBM FTP server.

#### How JES Mode Works Under the Hood:
```
[ Step 1: Secure Session ]
  CPM establishes TLS-encrypted session with Mainframe using Service (Reconcile) Account.
         ↓
[ Step 2: Switch to JES Mode ]
  CPM issues raw FTP command: SITE FILETYPE=JES
  (Tells z/OS: Do not write files to disk; route incoming stream directly to JES spool)
         ↓
[ Step 3: Dynamic JCL Injection ]
  CPM dynamically uploads a temporary JCL batch job running batch TSO program IKJEFT01.
         ↓
[ Step 4: Background Execution ]
  z/OS assigns JOBID (e.g., JOB01234), executes the security command in the background.
         ↓
[ Step 5: Spool Polling & Verification ]
  CPM fetches SYSTSPRT output log: GET JOB01234.X
  Scans for success code: TSS0300I PASSWORD MODIFIED (or RACF equivalent)
         ↓
[ Step 6: Cleanup ]
  CPM deletes the job from the spool: DELETE JOB01234 and closes the session.
```

#### The Injected JCL Payload (CA Top Secret / RACF):
```jcl
//CYBCHG   JOB (ACCOUNT),'CYBERARK PW RESET',CLASS=A,MSGCLASS=X
//STEP01   EXEC PGM=IKJEFT01
//SYSTSPRT DD SYSOUT=*
//SYSTSIN  DD *
 TSS REPLACE(TARGET_AID) PASSWORD(NEW_PASSWORD)
 TSS REPLACE(TARGET_AID) SUSPEND(NO)
/*
```
*(For IBM RACF environments, the payload substitutes `ALTUSER <target> PASSWORD(<new_password>) NOEXPIRED`).*


### Protocol & Port Testing Matrix

| Port / Protocol | Target Port | Status | Test Method | Result / Output |
| :--- | :--- | :--- | :--- | :--- |
| **Plain FTP** | TCP 21 | **Open** | `ftp.exe` | **Connected**: `220-FTPD1 IBM FTP CS V2R5`. Network routing is healthy. |
| **Explicit FTPS (EFTP)** | TCP 21 | **Rejected** | PowerShell Socket & `plink.exe -raw` sending `AUTH TLS` | **`534 Server is not willing to accept security mechanism`**. |
| **SSH** | TCP 22 | **Blocked** | Socket connection | **`Connection Refused / Timed Out`**. OpenSSH is either not running or blocked by firewalls. |
| **Implicit FTPS** | TCP 992 | **Closed** | Socket connection | **`Connection Refused`**. No implicit SSL daemon listening on 992. |

## 4. Technical Analysis: Why the Mainframe Threw Error `534`

The response `534 Server is not willing to accept security mechanism` is an RFC 2228/4217 compliance code from the **IBM z/OS Communications Server FTP daemon**:

1. **FTP Daemon Recognized the Command**:
   * It did not return `500 Unknown command` or `502 Command not implemented`. This confirms that the z/OS FTP server **has security/TLS capabilities installed and enabled**.
2. **TLS Is Rejected on Port 21**:
   * In the z/OS `FTP.DATA` configuration dataset, one of the following is configured:
     ```text
     SECURE_MECHANISM NONE
     ```
     *(disallows client-requested `AUTH TLS` on Port 21)*.
   * Or the system requires **AT-TLS (Application Transparent Transport Layer Security)** managed by Policy Agent (`PAGENT`), but:
     * Port 21 is not mapped to an active AT-TLS rule for the CPM IP subnet.
     * Or AT-TLS is bound to a **separate, custom secure port** (e.g., 990, 2121, etc.).

> **Security Mandate**: Plaintext FTP transmits user IDs and passwords across the network unencrypted. Because corporate policy prohibits cleartext transmission, **standard Port 21 cannot be used without TLS**.

## 5. Formal Questionnaire for the Mainframe Team

The following technical questions have been structured for the Mainframe Systems Programming and Security teams:

### 1. Approved Secure Connectivity Method
> **Question**: If encrypted communication is required for credential rotation, what is the approved secure connectivity method for CyberArk to communicate with z/OS LPARs?

### 2. Dedicated Secure FTP / AT-TLS Port
> **Question**: Is there a dedicated secure FTP/EFTP port configured on this LPAR, or is AT-TLS (Application Transparent TLS) being used to provide encryption on a custom port?
> * **Technical Context**: If AT-TLS governs Port 21 or a custom port, what client IP subnet policies or certificates must be configured in `PAGENT` so the IBM FTP daemon accepts the `AUTH TLS` exchange instead of returning `534`?

### 3. z/OS OpenSSH Availability
> **Question**: Is z/OS OpenSSH (`sshd`) enabled on the LPARs, and if so, what port is it listening on?
> * **Technical Context**: CyberArk's primary and most granular mainframe platform is `Policy-OS390SSH`, which operates through USS over SSH.

### 4. Firewall & Port 22 Access
> **Question**: Can TCP Port 22 (or the designated SSH port) be opened from the CyberArk CPM servers to the LPAR VIPAs?
> * **Technical Context**: Opening Port 22 enables the standard SSH/USS route, completely bypassing FTP/EFTP complexity.

### 5. Existing Mainframe Integration Components
> **Question**: Are there any existing CyberArk mainframe integration components, started tasks (e.g., CyberArk Mainframe Agent, CA-Top Secret / RACF connectors), or licensed plugins already deployed in the environment?

## 6. Implementation Roadmap (Post Mainframe Confirmation)

```mermaid
flowchart TD
    A["Mainframe Team Responds"] --> B{"Approved Protocol?"}
    
    B -- "Option 1: OpenSSH (Port 22)" --> C["1. Open TCP 22 Firewall (CPM to LPAR)<br/>2. Deploy Policy-OS390SSH (TPC)<br/>3. Verify SSH USS Login<br/>4. Manage Passwords via native passwd/TSS commands"]
    
    B -- "Option 2: Secure EFTP (TLS)" --> D["1. Obtain Custom EFTP Port & TLS Root CA<br/>2. Install z/OS CA cert into CPM Windows Store<br/>3. Configure Service Account with SUBMIT authority<br/>4. Deploy Policy-OS390FTP with JES mode (SITE FILETYPE=JES)<br/>5. Rotate Passwords via IKJEFT01 JCL batch jobs"]
```

### Detailed Next Steps for EFTP Deployment:
1. **Certificate Exchange**: Install the z/OS FTP server's Root/Intermediate CA certificate into the CPM Windows Certificate Store (`Trusted Root Certification Authorities`).
2. **Service Account Setup**:
   * Provision a dedicated privileged service account in CA Top Secret / RACF.
   * Grant `SUBMIT` authorization for batch jobs and administrative authority to issue `TSS REPLACE(...)` / `ALTUSER` against target accounts.
3. **Platform Configuration in PVWA**:
   * Duplicate the out-of-the-box `IBM OS390 FTP` platform.
   * Under Platform Settings $\rightarrow$ `ExtraInfo`, set `Port=<Custom_Port>` and configure FTPS/TLS parameters.
4. **Target Account Onboarding**:
   * Onboard target mainframe accounts.
   * Link the privileged Service Account as the **Reconcile Account**.
